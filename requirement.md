# OOP Simulation Group Project Summary

## Overview

- Build a visually interesting simulation in **Greenfoot**.
- Work in groups of **3 to 6** students; **4** is ideal.
- The simulation should:
  - fit on a **single screen**
  - have a clearly different **start state** and **end state**
  - include a **settings/parameters screen**
  - allow the user to influence setup, but **not directly control the simulation once it starts**
  - stay entertaining for at least **60 seconds**

## Core Requirements

- Use a **single Greenfoot scenario** with one main `World`.
- Extra worlds are allowed, such as:
  - `WelcomeWorld`
  - `StoryWorld`
  - `SettingsWorld`
  - `EndWorld`
- Include at least **two major superclasses**, each with at least **two subclasses**.
- All public classes, constructors, and methods need **API-style documentation**.
- Each class must include an `@author` tag naming the students who worked on it.
- Final code submission must be a `.gfar` file named like `Group9FactorySim.gfar`.

## Presentation Requirements

- Presentation length: **6 to 10 minutes**
- Must include:
  - an introduction to the simulation and important elements to watch
  - a live viewing of the simulation for **60 to 180 seconds**
  - discussion of **OOP benefits**, collaboration, challenges, and process improvements

## Project Phases

## Phase 1: Planning

1. Brainstorm and approve a simulation idea.
2. Build a simple basic `World` first.
3. Create a **concept-level** class diagram, then expand it into a **specification-level** class diagram with method signatures.
4. Divide superclass ownership and assign team roles.

## Phase 2: Coding

### GitHub workflow

- One member creates the GitHub repository and adds all teammates and the teacher.
- Use GitHub Desktop to **commit, push, pull, and merge**.
- Keep `main` stable and only push tested code that compiles and runs.
- Commit frequently with clear messages.
- Pull before starting work and push when finishing.
- Resolve merge conflicts together without overwriting teammates' work.

### Planning and communication

- Maintain a shared planning document with:
  - overall plan
  - current tasks
  - next steps
- Share the planning document with the teacher.
- Keep a group calendar for milestones.
- Reassess progress daily and reassign work when needed.

## Phase 3: Test and Polish

- Finish early enough to leave time for testing and refinement.
- Test the simulation across different user settings.
- Improve pacing, balance, graphics, sound, and overall clarity.

## Phase 4: Submit

Deliverables:

- `.gfar` export of the project
- specification-level class diagram
- individual contribution journals with daily entries and a final summary

## Phase 5: Presentation

- Introduce the simulation and possible outcomes.
- Show the simulation for **60 to 180 seconds**.
- Explain the role of **OOP** and the group’s collaboration process.

## Individual Accountability

Each student submits an **Individual Reflection Journal** containing:

- daily entries describing work completed each school day
- a final summary of contributions
- a reflection on teamwork and satisfaction with the result

The teacher states this document is confidential.

## Recommended Team Roles

- **Code Lead**: manages GitHub, integration, merges, and API consistency
- **Interface / Visual Design Lead**: handles UI, controls, displays, and viewer clarity
- **Graphics Lead**: manages art assets and possibly animation behavior
- **Audio Lead**: manages sound effects, music, levels, and pause behavior

Only **Code Lead** is strictly required, but the others are strongly recommended.

## Evaluation Criteria

- **Thinking (15 marks)**:
  - logical use of abstract/protected classes, variables, and methods
  - effective inheritance
  - appropriate use of `ArrayList`
  - solid application of Greenfoot programming skills

- **Communication (15 marks)**:
  - clear class and method names
  - thorough, concise documentation
  - required written task in the top block comment of the `World` class
  - strong visual presentation

- **Application (10 marks)**:
  - effective use of `ArrayList`, inheritance, and Greenfoot scenario-building in the project context

## Practical Checklist

- Approved simulation idea
- Basic `World` built early
- Specification-level class diagram completed
- Two major superclasses with two subclasses each
- Settings screen implemented
- Clear start and end states
- Stable GitHub workflow
- API documentation completed
- Graphics and audio polished
- `.gfar` exported correctly
- Presentation prepared
- Contribution journals completed
